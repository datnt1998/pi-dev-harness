# Spec: Method-cut review axes and evidence binding

> **Lifecycle:** update or delete this spec in the same change that alters the shipped discipline content below. The prose in `skills/` is the single source of truth; this spec records intent and acceptance for the change batch.
>
> **Motivating failures (field-tested downstream of this harness):** (a) subject-named review axes degenerate into conformance checking — a reviewer declared nine obligations "verified correct" while one harbored the only production defect; the falsification-framed axis found it. (b) Green proofs that held their own copy of an artifact (hand-written SQL, pre-aggregated fake rows) stayed green while the named behavior was broken. (c) Worker briefs that retyped the validation list silently dropped an entry. (d) Reds re-rolled as "flaky" trained sessions to ignore red. (e) A ticket batch left signed artifacts owned by no ticket; nothing surfaced it until failures. All items are re-phrased generically; no project vocabulary, model names, or tool-version specifics are imported.

## Goal

Review verdicts require attempted falsification instead of conformance reading; proofs must bind to the implementation rather than a copy of it; worker briefs carry mechanical bans and cite (never retype) the validation list; a red is diagnosed, never re-rolled; delegation staffing treats availability observations as decaying and verifies effective routes; and the readiness gate checks that every artifact the governing authority names is owned by exactly one ticket.

## Non-goals

- No changes to `lib/`, settings, README, or dependency surfaces (doc-plus-rename batch; one new reference file). Parent-authorized rename-only exceptions under R3: the axis-vocabulary pins and fixture labels in `tests/team-orchestration-policy.test.ts`, `tests/ticket-runner-extension.test.ts`, and `tests/team-orchestration-protocol.test.ts`, and the three axis-name mentions in `extensions/ticket-runner.ts` prompt strings — name-level swaps, no behavioral change.
- The sealed-reviewer machinery (capability seals, fingerprints, provenance, dispositions, degradation warnings) is untouched in substance — only axis names and axis method definitions change.
- No mutation-score tooling, no required table file format, no numeric thresholds.
- No model names, provider names, project names, or gate names from any source project.

## Requirements

- **R1 — Method-cut axes.** `skills/engineering-workflow/references/code-review.md` re-cuts the two axes by method, not subject:
  - **Axis A — Falsification**: attack the guards. For each behavior the diff's tests/validation claim to pin, name a meaning-changing mutation and state whether any guard dies. A mutation claim carries the pattern's before/after occurrence counts where applicable; DIED carries the observed red, SURVIVED is stated plainly. A red produced by a syntax error is not the needed red. "This provably cannot go red" is a permitted result when the structural reason is named; fabricating red or silently weakening a claim is a false claim.
  - **Axis B — Adversarial authority**: read each governing clause (spec, acceptance criteria, issue/request, repository standards docs) and **derive the input or scenario that would violate it before opening the implementation**, then check that the implementation refuses or handles it. Reading the code first anchors the reviewer into confirming it. An authority citation carries the literal quoted text, not a bare line number.
  - **Verdict rule:** PASS requires attempted falsification. "Verified correct" without a named mutation or violating input is a restatement of the diff, not a review result. A reviewer that ran no mutations and derived no violating inputs may report observations but may not clear the work.
  - **Framing rule:** briefs phrase checks as open adversarial questions ("confirm or refute: is this rule guarded at all?"), never as checklists of obligations to confirm — checklist framing invites confirmation. Before concluding a reviewer is weak, check whether it was asked a checklist question.
  - The smell baseline, review posture, AI-assisted-code risk lens, and pre-submit checklist survive as shared lenses: either axis may report such observations; observations never substitute for attack evidence in a verdict. Fixed-point resolution, the sealed stable-state machinery, provenance rules, disposition rules, and the final report section survive with axis names updated.
- **R2 — Parent mutates first.** Same file, parent duties: before staffing review, the parent runs a small number of quick mutations itself; a surviving mutant goes into the reviewer brief as a direct question. Mutation records are verified by sampling re-run of load-bearing rows — the parent personally re-runs the rows a verdict or fix round would rest on; a record is never accepted by format alone.
- **R3 — Axis-name synchronization.** Every surface naming the old axes is updated to the new names/methods with no other semantic change: `references/delegation-policy.md` (§6 brief line, §13 heading area and provenance line), `skills/engineering-workflow/SKILL.md` (router line and Code Review phase), `skills/pi-harness/references/engineering-workflow-integration.md` (checklist line), `skills/batch-implementation/SKILL.md` (loop step 4), `prompts/code-review.md` (description and axis list), `extensions/ticket-runner.ts` (three prompt-string mentions), and the lexical axis pins/fixture labels in the three named test files. Generic phrases ("both reviewer axes") are acceptable where a name is not needed.
- **R4 — Evidence binding.** New `skills/engineering-workflow/references/evidence-binding.md`, the single authority for what makes a proof binding:
  - A proof binds to the thing, not a copy: artifact text a proof carries (SQL, plans, projected rows, serialized output) is captured from the implementation at run time, or the site names which other guard actually bites. The test of a proof is a mutation of the implementation: change what the proof names and watch the proof die.
  - Expected values come from authority, never pasted back from the code's own output. A figure is either quoted from an authority (with citation) or derived from a named rule and labeled as such; neither may pretend to be the other. A test's name is a claim; when a defect was asserted under a name endorsing it, renaming the test is part of the fix.
  - Cardinality witnesses: a tie on every tie-broken sort key (for a nullable key, at least two rows in the null bucket); a parent with more than one child under every 1:many join with a limit or aggregate; a subject on the far side of every isolation boundary claimed proved. A distinguishing shape absent from the fixture leaves its branch unguarded.
  - Absence-shaped assertions carry a positive control — a subject the same probe must find the needle in; a probe that finds nothing anywhere is inert.
  - Tier blindness is declared, not discovered: when a contract's only guard lives in another test tier, the site or its spec says so, and a green run of the blind tier is never presented as covering it.
  - Cross-references: `tests-and-mocking.md` keeps ownership of tautological-test and mocking rules; `completion-evidence.md` keeps ownership of the completion record. One pointer each is added from `code-review.md` (Axis A), `tests-and-mocking.md`, and `completion-evidence.md`; the engineering-workflow SKILL reference list gains one line. No rule is restated across files.
- **R5 — Worker brief mechanics.** `skills/batch-implementation/SKILL.md` gains a short worker-brief section: every edit-tool entry carries both old and new text (deletion is an explicit empty replacement, never an omitted field), and after a failed or partial write the file is re-read from disk before the next edit; no prose, deliberation, or markdown fences in source files; no shell brace expansion for paths; if the same reasoning repeats more than twice, stop and report; never report a command not run, a number not measured, or an identifier not created (cross-reference `completion-evidence.md`). Validation lists are cited from the ticket/repository contract, never retyped into the brief; a brief may narrow the list only by naming what is skipped and why — a retyped list can silently drop an entry.
- **R6 — Red discipline.** `references/autonomous-execution.md` gains the rule: a red check is evidence and is diagnosed to root cause, never re-rolled until green; a red that recurs without a recorded diagnosis is a stop condition (added to the stop-conditions list); once a recorded flake is fixed, its color is believed again — re-rolling a repaired check is a violation, not caution. `skills/batch-implementation/SKILL.md`'s self-recovery bullet for flaky/transient failures is amended to require a recorded diagnosis before any retry, deferring to `autonomous-execution.md`. Cross-reference `diagnosing-bugs.md` for the diagnosis loop; do not restate it.
- **R7 — Staffing observations decay.** `references/delegation-policy.md` (§2 preflight or §10 control, worker's judgment on placement) gains: a reachability probe proves reachability, not capacity — when a routing change matters, probe with work-sized input; availability observations carry timestamps and decay — re-verify before staffing rather than re-reading a stale note; revival/resume paths may drop an explicit model override — after any revival, verify the effective route from run metadata (the existing effective-model verification rules own the mechanism), and prefer re-staffing with an explicit model when the override matters.
- **R8 — Authority coverage in the gate.** `skills/ticket-readiness/SKILL.md` Procedure gains an authority-coverage step beside the existing depth check: grep the governing spec/authority for every concrete artifact it names (files, symbols, schema objects, endpoints, commands, figures); each must be owned by exactly one ticket in the batch. An artifact owned by no ticket, owned by two, or a ticket ordering work on a structurally unreachable branch is reported as `NEEDS_DECISION` with the artifact named. Prose-level judgment; `lib/gate-run.ts` unchanged.

## Acceptance Criteria

1. Only the named files change; exactly one new file (`references/evidence-binding.md`); no `lib/`, README, or settings changes; `tests/` and `extensions/` changes are limited to the rename-only exceptions named in Non-goals.
2. Grep for the old axis names as axis labels returns no hits outside historical/spec context: every reviewing surface uses the method names or a generic phrase.
3. Single-authority: falsification/verdict/framing rules live in `code-review.md`; binding-proof rules live in `evidence-binding.md`; red discipline lives in `autonomous-execution.md`; each is cross-referenced elsewhere, never restated.
4. No numeric thresholds, no model/provider/project names, no table-format mandates in changed prose.
5. `npm test` (354/354) and `npm run pack:check` pass; file count grows by exactly the one new reference.

## Risks / Edge Cases

- The axis re-cut touches load-bearing normative prose in `delegation-policy.md` §13; edits there are name-level only — any semantic drift in seals/provenance/disposition rules is a blocker.
- Axis A needs runnable guards; for doc-only or non-executable diffs the falsification method degrades to deriving counter-examples — Axis A prose must allow "mutation" to mean any meaning-changing alteration whose detection is claimed, not only code mutations.
- R6 must not forbid legitimate bounded retries after diagnosis; the ban is on undiagnosed re-rolls.

## Validation Plan

`npm test`, `npm run pack:check`; two-axis sealed review run under the **new** method definitions (dogfood).
